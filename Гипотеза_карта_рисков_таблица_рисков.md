# Карта рисков: Гипотеза о контекстной фильтрации аномалий

## Гипотеза
Если мы добавим модуль контекстной фильтрации, который автоматически анализирует корреляцию между падением скорости и данными дорожных датчиков (температура полотна, осадки), а также учитывает суточные и недельные паттерны (ночные отстои фур, выходные дни), то доля ложных срабатываний снизится на 30%, потому что система перестанет реагировать на плановое снижение скорости из-за погоды и ночные стоянки грузовиков как на реальные инциденты.

**Метрика:** Доля ложных срабатываний (False Positive Rate)  
**Цель:** Снижение на 30%

---

## Матрица рисков

| Вероятность \ Последствия | Незначительные | Умеренные | Значительные |
|---|---|---|---|
| **Часто** | | | |
| **Вероятно** | | Отсутствие данных метеодатчиков или их низкое качество | Полное отсутствие доступа к метеоданным с дорожных датчиков |
| **Возможно** | Алгоритм требует ручной донастройки под каждый объект | Агрессивная фильтрация пропускает реальные инциденты | Суточные паттерны слишком разнообразны для формализации |
| **Редко** | Временные сбои в работе модуля фильтрации | | Полная замена системы на конкурентное решение |

## Детализация ключевых рисков

### 🔴 Критические риски (Значительные последствия)

#### 1. Полное отсутствие доступа к метеоданным с дорожных датчиков
- **Вероятность:** Вероятно
- **Последствия:** Невозможность реализовать контекстную фильтрацию по погоде, гипотеза не может быть проверена
- **Митигация:** 
  - Использовать открытые метеоданные (Росгидромет, погодные API)
  - Сфокусироваться на суточных/недельных паттернах без метеоданных
  - Упростить гипотезу до фильтрации только по временным признакам

#### 2. Суточные паттерны слишком разнообразны для формализации
- **Вероятность:** Возможно
- **Последствия:** Невозможность создать универсальные правила фильтрации, каждый объект требует индивидуальной настройки
- **Митигация:**
  - Использовать ML-подход (кластеризация паттернов) вместо жестких правил
  - Начать с пилота на 3-5 объектах с наиболее выраженными паттернами
  - Создать библиотеку типовых паттернов для масштабирования

---

###  Умеренные риски

#### 3. Отсутствие данных метеодатчиков или их низкое качество
- **Вероятность:** Вероятно
- **Последствия:** Частичная неработоспособность фильтрации, снижение эффективности
- **Митигация:**
  - Реализовать fallback-механизм (фильтрация только по временным признакам при отсутствии метео)
  - Добавить модуль очистки и валидации метеоданных
  - Использовать интерполяцию пропущенных значений

#### 4. Агрессивная фильтрация пропускает реальные инциденты
- **Вероятность:** Возможно
- **Последствия:** Рост False Negative Rate, снижение доверия к системе, пропуск реальных аварий
- **Митигация:**
  - Установить консервативные пороги фильтрации на старте
  - Внедрить A/B тестирование: сравнивать результаты «до» и «после»
  - Добавить флаг «подозрительный инцидент» для пограничных случаев

#### 5. Алгоритм требует ручной донастройки под каждый объект
- **Вероятность:** Возможно
- **Последствия:** Высокие трудозатраты на поддержку, невозможность масштабирования
- **Митигация:**
  - Автоматизировать подбор параметров через Grid Search
  - Создать шаблоны конфигураций для типовых объектов
  - Документировать процесс настройки

---

### 🟢 Низкие риски

#### 6. Временные сбои в работе модуля фильтрации
- **Вероятность:** Редко
- **Последствия:** Временная недоступность фильтрации, возврат к базовому алгоритму
- **Митигация:**
  - Реализовать graceful degradation (автоматический откат к базовому алгоритму)
  - Добавить логирование и мониторинг
  - Локальное кэширование данных

#### 7. Полная замена системы на конкурентное решение
- **Вероятность:** Редко
- **Последствия:** Проект становится нерелевантным
- **Митигация:**
  - Невозможно контролировать, но маловероятно в рамках семестра
  - Сфокусироваться на создании универсального модуля, который можно интегрировать в любую систему

|---|---|---|---|---|

# Что может помешать гипотезе сработать

> Начинаем с предположений, ошибка в которых делает решение бесполезным.

| Предположение | Если неверно... | Быстрая проверка |
|---|---|---|
| Есть доступ к сырым 5-минутным данным с радаров | Невозможно провести ретроспективный анализ и валидацию алгоритма | Запросить тестовую выгрузку у заказчика в первую неделю |
| Данные метеодатчиков доступны и сопоставимы с данными радаров по времени | Контекстная фильтрация по погоде не может быть реализована | Попытаться стыковать выборку трафика с метеоданными за 1 неделю |
| Суточные и недельные паттерны трафика стабильны и формализуемы | Правила фильтрации не будут работать универсально, потребуется ручная настройка под каждый объект | Построить графики интенсивности по часам/дням недели для 3–5 объектов |
| Текущий алгоритм действительно генерирует >30% ложных срабатываний | Проблема преувеличена, и пространство для улучшения минимально | Проанализировать выборку из 50–100 последних алертов вручную |
| ML-модель способна выявить скрытые паттерны (ночные отстои фур, погодные замедления) | Модель не даст значимого улучшения по сравнению с эвристическими правилами | Запустить базовый Isolation Forest на выборке за 1 месяц |
| Данные достаточно чистые (нет критических пропусков и рассинхрона) | Пропуски и шум сделают анализ недостоверным | Посчитать долю пропусков и выбросов в тестовой выборке |
| Заказчик готов предоставить обратную связь по результатам анализа | Не сможем валидировать выводы и скорректировать подход | Согласовать формат и частоту встреч с наставником от заказчика |


## Резюме

**Наиболее критичные риски:**
1. Отсутствие доступа к метеоданным (блокирующий риск)
2. Слишком большое разнообразие паттернов (риск нереализуемости гипотезы)

**Стратегия:**
- Начать с упрощенной версии (фильтрация только по временным паттернам)
- Параллельно решать вопрос доступа к метеоданным
- Запустить пилот на 3-5 объектах для валидации подхода перед масштабированием

**Критерии остановки:**
- Если на пилотных объектах точность фильтрации <50%
- Если False Negative Rate вырос более чем на 10%
